# Renew Curve v9 開發流程

文件狀態：初版開發基準。

需求來源：[v9 專案規格與畫面流程](./v9%20專案規格與畫面流程.md)

驗證依據：[v9 驗證目標](./v9%20驗證目標.md)

## 1. 文件目的

本文件定義 Renew Curve v9 的實作順序、每個里程碑的輸入與產出、開發期間的固定檢查節奏，以及進入下一階段前必須通過的品質門檻。

本文件回答「現在應該做什麼」；功能是否正確則由 `v9 驗證目標.md` 的 `VAL-*` 項目判定。若需求、開發流程與驗證目標互相矛盾，以專案規格為需求來源，先修正文書再繼續實作。

## 2. 開發原則

- v9 使用獨立的 `renew_curve_v9/` 專案目錄，不直接把 v8 當成 v9 繼續修改。
- v8 程式只能作為技術參考，不匯入 v8 資料，也不保留 CSV、難易度或舊通知流程。
- 先完成可獨立測試的 Domain 與資料層，再讓 UI 呼叫 Application Service。
- UI 不直接查詢 SQLite、建立 ZIP 或管理 Gmail 認證。
- 每項功能開始前先找出對應的 `VAL-*` 編號與通過條件。
- 先建立或更新測試，再完成實作，最後留下可重現的驗證證據。
- 跨多張資料表、批次排程、匯入及還原操作必須可 rollback 或完整恢復。
- 不以「畫面看起來正常」代替資料、錯誤路徑與安全測試。
- 任何規格變更都依序更新：專案規格 → 驗證目標 → 開發流程／程式碼。

## 3. 建議專案結構

```text
renew_curve_v9/

├── README.md

├── src/

│       ├── config.py
│       ├── domain/
│       ├── application/
│       ├── infrastructure/
│       └── ui/
├── resources/
│   └── icons/
├── tests/
│   ├── unit/

│   ├── gui/
│   ├── security/
│   └── fixtures/

```

`artifacts/verification/` 用於保存可重現的驗證輸出、畫面截圖及打包驗收紀錄；不得放入 Gmail token、使用者任務內容或其他敏感資料。

## 4. 固定開發循環

每個功能都使用相同循環：

```text
選定功能與對應 VAL ID
  ↓
確認規格與通過條件
  ↓
建立或調整失敗測試
  ↓
實作最小完整功能
  ↓
執行受影響的 unit / integration / GUI 測試
  ↓
檢查相依功能與禁止項目
  ↓
更新驗證狀態與證據
  ↓
完成小範圍提交
```

若在實作中發現通過條件無法客觀判定，應先修正驗證目標，不可自行猜測後繼續擴大實作。

## 6. M0：專案骨架與基準環境

### 6.1 目標

建立不依賴 v8 執行環境的 v9 專案，確認安裝、import、GUI 啟動與測試入口可用。

### 6.2 工作項目

- 建立 `renew_curve_v9/`、`src/renew_curve/` 與測試目錄。
- 建立 `pyproject.toml`，區分正式與開發依賴。
- 建立 `renew_curve.spec`、應用程式入口及基本主視窗。
- 建立 Local AppData 路徑解析與測試用資料目錄注入機制。
- 建立統一 logging 與未預期例外處理入口。
- 建立 pytest、pytest-qt 及基本 smoke test。
- 建立測試 fixture，確保測試不寫入真實使用者資料目錄。
- 建立 lint／格式化／型別檢查工具設定；實際工具可由實作團隊選定。

### 6.3 對應驗證

- `VAL-APP-*`
- `VAL-GUI-001`
- `VAL-ABSENCE-*`

### 6.4 離開條件

- editable install 成功。
- `compileall` 與基礎 pytest 通過。
- 主視窗可在測試資料目錄啟動及關閉。
- 啟動失敗不會覆蓋既有資料。
- v9 專案未依賴 v8 CSV、難易度或通知程式碼。

## 7. M1：Domain 核心規則

### 7.1 目標

先以純 Python 完成不依賴 PySide6、SQLite 或 Gmail 的核心規則。

### 7.2 工作項目

- 建立 Task、ReviewSchedule、ReviewRecord 等 domain model 與 enum。
- 實作固定 1、3、7、14、30、60、90、120、180、365 天曲線。
- 實作 3 至 10 次選擇、開始時間加 N 個 24 小時及時分保留。
- 實作手動日期排序、重複與開始時間驗證。
- 實作只依 Windows 本機日期判定今日與逾期。
- 實作完成、略過、未完全完成與完成率規則。
- 實作任務狀態優先順序與狀態轉換。
- 實作暫停天數與恢復後排程順延。
- 實作整批推到明天及重複排程合併規則。
- 實作排程重建、歷史保留及複習次數下限驗證。

### 7.3 對應驗證

- `VAL-SCHEDULE-*`
- `VAL-DATE-*`
- `VAL-REVIEW-*`
- `VAL-TASK-006` 至 `VAL-TASK-010`

### 7.4 離開條件

- Domain 不 import PySide6、sqlite3 或 Gmail SDK。
- 所有核心規則均有正常、邊界及錯誤案例單元測試。
- 測試涵蓋跨日、跨月、跨年、略過、暫停及重複合併。
- M1 對應的所有 P0 驗證均通過。

## 8. M2：SQLite 與 Repository

### 8.1 目標

建立可 migration、可 rollback 並保持資料一致性的 SQLite 資料層。

### 8.2 工作項目

- 建立連線管理，固定啟用 Foreign Key，並評估 WAL mode。
- 建立 `schema_migrations` 及第一版 schema。
- 建立 tasks、review_schedules、review_records、categories、tags、task_tags、settings、assets 與 backup_logs。
- 為查詢日期、狀態、任務關聯與搜尋欄位建立必要索引。
- Repository 查詢全部使用參數化 SQL。
- 實作任務建立、編輯、刪除、暫停、封存及還原。
- 實作排程批次建立、重建、完成、略過、推延與合併。
- 實作狀態與完成率重新計算後寫回資料庫。
- 實作交易失敗 rollback、foreign key cascade 與 `PRAGMA integrity_check`。

### 8.3 對應驗證

- `VAL-DB-*`
- `VAL-TASK-*`
- `VAL-REVIEW-*`
- `VAL-SECURITY-001`

### 8.4 離開條件

- 所有 CRUD 與批次操作均有 integration test。
- 中途注入錯誤時，交易不留下半套資料。
- 刪除任務後無孤立排程、紀錄及標籤關聯。
- migration 可從空資料庫可靠建立目前 schema。
- M2 對應的所有 P0 驗證均通過。

## 9. M3：Application Service

### 9.1 目標

將 Domain 與 Repository 組合成 UI 可呼叫的完整使用案例。

### 9.2 工作項目

- 實作 TaskService、ReviewService 與 SettingsService。
- 定義 DTO／result object，避免 UI 接觸 SQL row 或底層例外。
- 實作任務新增、編輯、複製、刪除、暫停、恢復、封存及還原。
- 實作排程預覽及變更差異預覽。
- 實作今日、逾期、未來 7 天、月曆數量及統計摘要查詢。
- 實作搜尋、分類、標籤、篩選與排序。
- 實作使用者可理解的錯誤分類與訊息。

### 9.3 對應驗證

- `VAL-TASK-*`
- `VAL-REVIEW-*`
- `VAL-SEARCH-*`
- `VAL-CALENDAR-*`

### 9.4 離開條件

- 完整使用案例可在沒有 GUI 的測試中執行。
- UI 所需查詢都有明確 service API。
- Service 操作失敗不會留下不一致資料。
- M3 對應的所有 P0 與 P1 驗證均通過。

## 10. M4：主要 UI 與導覽

### 10.1 目標

完成使用者可從介面操作的主要工作流程。

### 10.2 工作項目

- 建立 app shell、導覽狀態及頁面切換。
- 完成儀表板、任務管理、今日複習、月曆及設定頁。
- 完成新增／編輯任務與排程預覽對話框。
- 完成完成、略過、推到明天、編輯時間及任務詳細資料操作。
- 完成搜尋、篩選、排序與結果數量即時更新。
- 完成確認、成功、失敗與取消流程。
- 確保長時間操作可交給 worker，UI 不阻塞。
- 檢查鍵盤操作、1280×720、1920×1080 與高 DPI。

### 10.3 對應驗證

- `VAL-GUI-*`
- `VAL-TASK-*`
- `VAL-REVIEW-*`
- `VAL-SEARCH-*`
- `VAL-CALENDAR-*`

### 10.4 離開條件

- 使用者可只靠 UI 完成新增、複習及管理流程。
- 所有主要 GUI 測試通過。
- 重要操作都有確認或結果提示。
- 常見解析度與縮放下沒有阻斷操作的裁切或遮蔽。

## 11. M5：個人化素材

### 11.1 目標

完成背景、貼圖及安全素材儲存，不依賴來源檔案的絕對路徑。

### 11.2 工作項目

- 實作 PNG、JPG、JPEG、WebP 選取與實際解碼驗證。
- 實作 20 MB 單檔限制。
- 將素材複製至 Local AppData 並只保存相對路徑。
- 實作背景全域套用與指定頁面模式。
- 實作固定位置、固定大小的貼圖與啟用／停用。
- 刪除使用中素材時回復內建預設或停用。
- 補齊素材資料庫、檔案失敗與 rollback 測試。

### 11.3 對應驗證

- `VAL-ASSET-*`
- `VAL-SECURITY-002`

### 11.4 離開條件

- 支援格式可正常顯示，不支援或偽造格式會被拒絕。
- 素材來源檔移動或刪除後，應用程式內副本仍可用。
- 資料庫與素材檔案不會因失敗操作失去同步。

## 12. M6：備份與完整取代匯入

### 12.1 目標

建立可以驗證、完整還原，且失敗時不破壞目前資料的 ZIP 備份流程。

### 12.2 工作項目

- 使用 SQLite backup API 建立一致性 snapshot。
- 建立 manifest、檔案清單、大小及 SHA-256 checksum。
- 收集資料庫、背景與貼圖並產生 ZIP。
- 匯入前驗證格式版本、schema 版本、checksum、路徑與資料庫完整性。
- 在暫存目錄解壓縮，防止路徑穿越。
- 匯入前建立目前資料的還原備份。
- 實作資料庫與素材的完整取代及失敗恢復。
- 排除 OAuth token、既有 backups ZIP 與文字 log。
- 匯入成功後關閉舊連線並要求重新啟動。
- 顯示未加密 ZIP 警告。

### 12.3 對應驗證

- `VAL-BACKUP-*`
- `VAL-IMPORT-*`
- `VAL-SECURITY-003` 至 `VAL-SECURITY-006`

### 12.4 離開條件

- 正常備份可在新的測試資料目錄完整還原。
- 每一種錯誤 ZIP 都不會改變目前資料。
- 資料庫與素材只能一起成功或一起恢復。
- 所有匯入測試均使用暫存資料，不接觸真實使用者資料。

## 13. M7：Gmail OAuth 與寄送

### 13.1 目標

完成首次授權一次、後續跨程式重啟直接寄送的 Gmail 備份流程。

### 13.2 工作項目

- 建立發布者持有的 Google Cloud 專案、Desktop app OAuth client 與 Gmail API 設定。
- 僅要求 `gmail.send` 及顯示帳號所必要的最小權限。
- 使用系統預設瀏覽器、loopback redirect、`state` 與 PKCE。
- 首次授權要求 offline access，取得 refresh token。
- 使用 Windows Credential Manager 或等效機制保存 token。
- 實作程式重啟後靜默更新 access token。
- 實作 token 失效時，在使用者主動寄送時重新授權。
- 實作連結、重新授權、解除連結與帳號狀態 UI。
- 實作預設收件人、郵件本文、ZIP 附件與寄送紀錄。
- 實作網路、授權、附件大小及 Gmail API 錯誤處理。
- 確認成功與失敗都保留 ZIP，且程式關閉後不寄送。
- 正式散布前完成 OAuth Production 設定及必要驗證。

### 13.3 測試策略

- 自動化測試使用 fake OAuth／Gmail client，不使用真實認證。
- M7 完成時使用專用測試帳號做一次真實首次授權與寄送。
- 關閉並重新開啟程式後，再做一次不出現登入頁的真實寄送。
- 發布候選版再執行一次完整真實帳號 smoke test。
- 測試證據不得包含 token、完整郵件內容或使用者資料。

### 13.4 對應驗證

- `VAL-GMAIL-*`
- `VAL-SECURITY-007` 至 `VAL-SECURITY-009`

### 13.5 離開條件

- 一般使用者不需要輸入密碼、API key、client secret 或編寫認證文件。
- 首次授權完成後，跨程式重啟可直接寄送。
- token 失效有清楚且可恢復的重新授權流程。
- Gmail 完全失效時，本機任務與 ZIP 備份仍正常。

## 14. M8：整合、效能、打包與發布

### 14.1 目標

在完整資料量、常見畫面環境及乾淨 Windows 環境中證明 v9 可以發布。

### 14.2 工作項目

- 執行 compileall 與完整 pytest。
- 以 5,000 個任務、50,000 筆排程執行效能驗證。
- 驗證冷啟動、儀表板與搜尋篩選時間門檻。
- 驗證 1280×720、1920×1080，以及 100%、150%、200% 縮放。
- 建立 PyInstaller onedir 版本並先做診斷。
- 建立正式發布版本。
- 在沒有 Python 的乾淨 Windows 10／11 環境測試。
- 執行真實 Gmail smoke test、備份與還原演練。
- 檢查 release 內容不含資料庫、token、測試帳號或本機路徑。
- 完成 `VAL-ABSENCE-*`，確認排除功能沒有回流。

### 14.3 對應驗證

- `VAL-PERF-*`
- `VAL-PACKAGE-*`
- 所有 P0、P1 與適用的 P2 驗證。

### 14.4 離開條件

- 所有 P0、P1 驗證通過。
- 沒有未處理的資料損毀、安全或認證問題。
- 自動化測試全部通過。
- 打包成品通過乾淨 Windows 驗收。
- 發布驗證證據已保存且不含敏感資料。

## 15. 驗證執行節奏

### 15.1 每次程式碼修改

- 執行受影響模組的 unit test。
- 執行「變更影響對照」要求的相依測試。
- 確認沒有新增明顯 TODO、pass 或測試用隱藏入口。

### 15.2 每個功能完成

- 執行該功能全部 unit、integration 及適用的 GUI 測試。
- 更新對應 `VAL-*` 最新狀態及證據。
- 檢查錯誤路徑、取消流程及資料不變性。

### 15.3 每個里程碑完成

- 執行完整 pytest。
- 執行該里程碑的手動驗收。
- 確認所有 P0、P1 項目通過。
- 將仍未處理的 P2 問題記錄原因與處理時機。

### 15.4 發布候選版

- 執行所有自動化與安全測試。
- 執行效能基準、GUI 尺寸／DPI 驗收及乾淨 Windows 打包驗收。
- 執行真實 Gmail、完整備份與完整取代還原演練。
- 檢查禁止功能與敏感檔案。

## 16. 標準驗證指令

```powershell
py -3.10 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m compileall -q src tests
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m PyInstaller --clean --noconfirm renew_curve.spec
```

依實際工具設定，可另外加入 lint、format check、type check 及效能測試指令。所有正式指令應可由專案根目錄非互動執行。

| PyInstaller 或資源 | Package、啟動、素材、SQLite、Gmail 認證錯誤 |

## 18. 阻塞與偏差處理

- `BLOCKED` 只能用於缺少外部條件、規格決策或必要測試環境的項目。
- 測試失敗應標為 `FAIL`，不可用 `BLOCKED` 取代。
- 任何暫時偏離規格的實作都必須列出受影響的 `VAL-*`、原因及移除期限。
- P0 失敗時停止擴大該功能，先修復或回復到可驗證狀態。
- Gmail、打包或乾淨 Windows 等外部環境暫時不可用時，仍應完成 fake／local 測試並保留未完成的真實驗收項目。

## 19. 開發完成定義

功能只有在以下條件全部成立時才算完成：

- 實作符合目前規格。
- 對應 `VAL-*` 已存在且通過。
- 正常、邊界及失敗案例都有適當測試。
- 沒有繞過 Service Layer 或資料安全規則。
- UI 有清楚的成功、失敗或確認回饋。
- 驗證證據可由其他人重現。
- 沒有把 token、真實資料、絕對使用者路徑或秘密加入專案。

v9 只有在 M0 至 M8 全部完成，且 `v9 驗證目標.md` 的發布 Gate 通過後，才可判定為可發布。
