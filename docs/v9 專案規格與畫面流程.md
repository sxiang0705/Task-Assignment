# Renew Curve v9 專案規格與畫面流程

文件狀態：需求草案，供後續批改、校正與實作使用。

本文件描述 Renew Curve v9 的目標、功能範圍、資料設計、備份與 Gmail 寄送流程、畫面流程，以及專案完成後的驗證方式。

相關執行文件：

- [v9 開發流程](./v9%20開發流程.md)
- [v9 驗證目標](./v9%20驗證目標.md)

v9 會保留 v8 的「遺忘曲線複習」核心概念，但重新設計使用流程與介面。v8 僅作為參考，不需要匯入 v8 資料，也不需要保留 CSV 相容功能。

## 1. 專案目的

Renew Curve 是一套 Windows 桌面版的學習複習管理工具，協助使用者針對學習內容建立任務，依固定的遺忘曲線安排複習時間，並追蹤每次複習的完成狀態。

專案主要要解決的問題是：使用者知道需要複習，但不容易記得何時複習、哪些內容已經複習，以及哪些內容已經逾期。

本應用程式的核心目的包括：

- 建立與管理學習任務。
- 使用固定遺忘曲線安排複習日期。
- 顯示今日、近期與逾期的複習項目。
- 讓使用者記錄每次複習是否完成。
- 提供任務搜尋、分類與基本進度查看。
- 將資料庫、背景與貼圖集中備份到 ZIP 檔案。
- 由使用者手動將備份 ZIP 寄送到 Gmail，方便保存與追蹤。

## 2. 專案目標與範圍

### 2.1 目標平台

- 主要平台：Windows 桌面環境。
- 介面語言：目前以中文為主。
- 使用模式：單一使用者、單機、local-first。
- 程式關閉時不執行複習通知或 Gmail 寄送。
- 不需要手機版、Web 版或多人協作。

### 2.2 技術方向

- UI：PySide6。
- DBMS：SQLite。
- 備份格式：ZIP。
- Gmail 寄送：Gmail API OAuth 2.0。
- 打包：PyInstaller Windows executable。

### 2.3 v9 包含的功能

- 任務新增、編輯、刪除與封存。
- 固定遺忘曲線排程。
- 手動複習日期排程。
- 今日複習與逾期項目查看。
- 完成、推延與略過複習項目。
- 月曆查看複習日期。
- 任務搜尋、分類、標籤與篩選。
- 基本數量與完成率摘要，但不製作統計圖表。
- 自訂背景與貼圖。
- SQLite 資料庫備份與還原。
- 備份資料匯出成 ZIP。
- ZIP 完整取代式匯入。
- 手動寄送備份 ZIP 到 Gmail。
- 本機寄送紀錄與結果追蹤。

### 2.4 v9 不包含的功能

- Windows 桌面通知。
- 跳到主畫面的提醒彈跳視窗。
- 程式關閉後的背景提醒。
- 程式關閉後的自動 Gmail 寄送。
- CSV 匯入與匯出。
- v8 舊資料匯入。
- ZIP merge 匯入。
- 複習完成後自動產生新的複習。
- 依難易度調整排程。
- 難易度欄位。
- 統計圖表。
- 雲端同步。
- 帳號登入與多人協作。
- 手機或 Web 版本。

## 3. 詳細功能規格

### 3.1 應用程式外框與導覽

應用程式需要有清楚的主要導覽，但導覽列不限定一定放在左側。實際位置可依畫面空間、使用性與視覺設計決定，可能放在上方、側邊或使用分頁結構。

導覽項目建議包括：

- 儀表板。
- 任務管理。
- 今日複習。
- 月曆。
- 資料與備份。
- 個人化設定。

導覽設計應符合以下要求：

- 目前所在頁面要有明確狀態。
- 重要功能不能被隱藏在測試用按鈕中。
- 小尺寸視窗下仍能使用。
- 支援鍵盤操作。
- 不依賴固定的單一螢幕解析度。

### 3.2 儀表板

儀表板是使用者開啟程式後看到的主要頁面。

應顯示：

- 今日待複習數量。
- 逾期複習數量。
- 未來 7 天（包含今天）的複習數量。
- 任務總數。
- 已完成與未完成複習數量。
- 基本完成率。
- 最近新增的任務。
- 即將到期的複習項目。

應提供快速操作：

- 新增任務。
- 開始今日複習。
- 查看逾期項目。
- 開啟月曆。
- 建立資料庫備份。
- 建立並寄送 Gmail 備份。

儀表板只顯示數字、清單與摘要，不需要統計圖表。

### 3.3 任務管理

任務代表使用者想要學習或複習的一個主題。

任務欄位包括：

- 任務名稱：必填。
- 任務說明或筆記：選填。
- 分類：選填。
- 標籤：選填，可有多個。
- 開始時間：必填。
- 複習排程方式：遺忘曲線或手動輸入。
- 複習次數：遺忘曲線模式使用。
- 任務狀態。
- 建立時間。
- 最後修改時間。

不使用難易度欄位，也不根據難易度改變複習排程。

任務狀態包括：

- 未開始。
- 進行中。
- 有待複習項目。
- 有逾期項目。
- 已完成。
- 未完全完成。
- 已暫停。
- 已封存。

任務目前狀態應儲存在資料庫中。`TaskService` 應在應用程式啟動、本機日期變更，以及任務、排程或複習狀態異動後重新計算並寫回，避免狀態因時間經過而失真。

狀態判定優先順序為：已封存、已暫停、已完成、未完全完成、有逾期項目、有待複習項目、未開始、進行中。當所有排程都完成時為「已完成」；當已無待處理排程，但至少有一筆略過紀錄時為「未完全完成」；有排定在今天的待處理項目時為「有待複習項目」；開始日期尚未到達時為「未開始」；其餘已開始且仍有未來排程的任務為「進行中」。

暫停任務時記錄暫停日期。恢復任務時，依暫停的本機日曆天數，將所有尚未完成且尚未略過的排程等量順延；暫停期間不累積逾期。已封存任務在畫面與統計上以「已封存」為準。

任務操作包括：

- 新增任務。
- 編輯任務內容。
- 編輯複習日期。
- 刪除任務。
- 暫停任務。
- 恢復暫停任務。
- 封存任務。
- 還原封存任務。
- 複製任務。
- 搜尋任務。
- 依狀態、分類、標籤或日期篩選。
- 依任務名稱、建立時間或下一次複習時間排序。

刪除任務前必須顯示確認視窗。刪除後，該任務的複習排程與複習紀錄也應依資料庫規則一併處理，不可留下孤立資料。

### 3.4 遺忘曲線排程

v9 使用固定的遺忘曲線，不依使用者評分或難易度動態調整。

預設複習間隔為：

```text
第 1 天、 第 3 天、 第 7 天、 第 14 天、 第 30 天、
第 60 天、 第 90 天、 第 120 天、 第 180 天、 第 365 天
```

使用者可選擇 3 至 10 次複習。系統會依開始時間產生對應的複習日期與時間。「第 1 天」明確定義為開始時間加 24 小時，其餘間隔依相同方式計算，並保留本機牆上時間的時分。

遺忘曲線功能包括：

- 自動產生複習日期。
- 保留開始時間的時分。
- 顯示產生後的日期預覽。
- 編輯尚未完成的複習日期。
- 防止複習日期重複。
- 防止複習日期早於開始時間。
- 不因完成複習而額外產生新複習。

修改開始時間、複習次數或切換排程模式時，必須重建尚未處理的排程，並在儲存前顯示差異預覽。已完成、已略過的項目及其歷史紀錄必須保留。若新的複習次數低於「已完成數＋已略過數」，應拒絕修改並說明原因。

手動排程功能包括：

- 使用者自行輸入每次複習時間。
- 日期不可重複。
- 日期應依時間排序。
- 日期不可早於任務開始時間。
- 建立前先顯示預覽。

### 3.5 複習流程

今日複習頁面應顯示：

- 今日待複習項目。
- 逾期項目。
- 任務名稱。
- 任務分類與標籤。
- 任務筆記。
- 第幾次複習。
- 預定複習時間。
- 目前任務完成率。

每筆複習項目提供：

- 完成。
- 推延。
- 略過。
- 編輯複習時間。
- 開啟任務詳細資料。

完成複習後：

- 該筆複習紀錄標記為完成。
- 任務完成率重新計算。
- 已完成項目不再出現在待複習清單。
- 若所有排程都完成，任務狀態變為已完成。
- 不自動產生額外複習。

略過複習後：

- 該筆排程標記為略過，並寫入不可復原的歷史紀錄。
- 略過不算完成，不能使任務成為「已完成」。
- 略過項目計入完成率的分母，但不計入分子，因此會降低完成率。
- 略過項目不再出現在待複習清單，也不再被推延。
- 若已無待處理項目但至少有一筆略過，任務狀態變為「未完全完成」。

推延預設採整批「推到明天」。系統應將目前項目與同一任務所有後續尚未完成、尚未略過的項目，各自增加一個本機日曆日並保留原時分；已完成及已略過項目不受影響。若推延後與同一任務的另一筆待處理排程產生完全相同的日期時間，應合併成一筆排程，複習總次數隨之減少，並在 `review_records` 保留合併操作紀錄。若使用者需要其他日期，應使用「編輯複習時間」。

### 3.6 逾期項目

逾期只依使用者的 Windows 本機日期判定，不比較當日的時分。預定日期早於今天，且尚未完成或略過的項目才標記為逾期；排定在今天的項目整天都屬於今日待複習，不另外算作逾期。已暫停與已封存任務不計入今日或逾期清單。

逾期頁面或篩選結果應能：

- 顯示所有逾期項目。
- 依逾期時間排序。
- 一次完成。
- 一次推延。
- 編輯日期。
- 封存或刪除所屬任務。

v9 不需要使用 Windows 通知提醒逾期項目；使用者開啟程式後即可在介面中查看。

### 3.7 月曆

月曆應顯示複習排程的日期分布。

功能包括：

- 月檢視。
- 切換月份。
- 回到今天。
- 顯示每日待複習數量。
- 標示逾期項目。
- 點擊日期查看該日複習項目。
- 從日期頁面開啟複習或編輯排程。

月曆只需要清楚呈現數量與狀態，不需要複雜圖表。

### 3.8 搜尋、分類與篩選

搜尋範圍包括：

- 任務名稱。
- 任務說明。
- 分類。
- 標籤。

篩選條件包括：

- 今日待複習。
- 逾期。
- 進行中。
- 已完成。
- 未完全完成。
- 已暫停。
- 已封存。
- 指定分類。
- 指定標籤。
- 指定日期區間。

篩選與搜尋結果應能即時更新，並顯示目前結果數量。

### 3.9 基本統計摘要

v9 不製作統計圖表，但可提供基本文字或數字摘要：

- 任務總數。
- 待複習數量。
- 逾期數量。
- 已完成複習數量。
- 未完成複習數量。
- 總完成率。

這些數值可出現在儀表板或資料頁面中。

統計口徑如下：

- 任務總數、各項複習數量及總完成率均排除已暫停與已封存任務。
- 略過項目不列入已完成數；未完成複習數包含待處理與已略過項目。
- 任務完成率及總完成率皆為「已完成複習數 ÷ 全部排程數 × 100%」。略過項目保留在分母但不進入分子。
- 未來摘要固定顯示從今天起算、包含今天的 7 個本機日曆日。

### 3.10 自訂背景與貼圖

自訂背景與貼圖功能保留。

使用者可以：

- 上傳背景圖片。
- 上傳貼圖。
- 選擇目前使用的背景。
- 選擇目前使用的貼圖。
- 啟用或停用貼圖。
- 刪除已上傳素材。
- 背景可使用「全域套用」或「指定頁面」兩種模式。

素材實際檔案應放在應用程式資料目錄中，資料庫只儲存相對路徑與設定。不可依賴某台電腦上的絕對路徑。

背景與貼圖支援 PNG、JPG、JPEG 與 WebP，單一檔案上限為 20 MB；匯入時必須實際解碼驗證，不可只依副檔名判斷。貼圖使用介面定義的固定位置與固定大小，不提供使用者調整位置或尺寸。刪除正在使用的素材時，應自動改回內建預設素材或停用該素材。

### 3.11 資料庫備份

備份只針對新版 SQLite 資料與素材，不需要 CSV，也不需要處理 v8 舊資料。

備份 ZIP 建議結構如下：

```text
renew-curve-backup.zip
├── manifest.json
├── database.sqlite3
└── assets/
    ├── backgrounds/
    └── stickers/
```

`manifest.json` 至少應記錄：

- 備份格式名稱。
- 備份格式版本。
- 應用程式版本。
- SQLite schema 版本。
- 備份建立時間。
- 包含的檔案清單。
- 每個檔案的大小。
- 每個檔案的 checksum。

建立備份時應使用 SQLite 安全備份流程，不應在資料正在寫入時直接複製可能不完整的資料庫檔案。

### 3.12 ZIP 匯入

v9 的資料匯入只支援 ZIP，且目前只支援「完整取代目前資料」。

匯入流程：

1. 使用者選擇 ZIP 檔案。
2. 驗證 ZIP 是否為 Renew Curve 備份。
3. 驗證 manifest、格式版本與 checksum。
4. 驗證資料庫可以開啟。
5. 執行資料庫完整性檢查。
6. 驗證 ZIP 內的路徑不能離開暫存資料夾。
7. 先建立目前資料的還原備份。
8. 將 ZIP 解壓縮到暫存位置。
9. 確認資料庫與素材都完整後，才替換目前資料。
10. 將素材路徑轉換為目前資料目錄下的相對路徑。
11. 關閉目前資料庫連線，提示使用者重新啟動應用程式。

匯入失敗時：

- 不可破壞目前資料。
- 不可只替換資料庫而遺失素材。
- 應保留匯入前的備份。
- 應顯示清楚的錯誤原因。

ZIP 不需要加密，但文件與介面應提醒使用者：未加密 ZIP 內的任務內容可以被看到。

完整取代的範圍包括資料庫內的任務、排程、複習歷史、分類、標籤、個人化設定、素材資料、備份紀錄與 Gmail 寄送紀錄，以及 ZIP 內的背景與貼圖實體檔案。Gmail OAuth token、其他認證資料、目前 `backups` 目錄中的既有 ZIP 與 logs 目錄中的文字日誌不得由匯入 ZIP 取代。

匯入只接受與目前應用程式完全相同的備份格式版本與 SQLite schema 版本，不在匯入流程中遷移舊版 schema。完整匯入成功後，應提示使用者重新啟動應用程式；重新啟動前不得繼續操作已被取代的資料庫連線。

### 3.13 Gmail 手動寄送備份

Gmail 功能只由使用者手動觸發，不執行背景排程。同一個 Gmail 帳號正常情況下只需要完成一次 OAuth 授權；授權成功後，即使關閉並重新開啟程式，使用者也可直接按下寄送，不需要再次登入。

一般使用者不需要輸入 Gmail 密碼、API key、OAuth client secret，也不需要自行建立或編寫認證文件。OAuth 用戶端身分由 Renew Curve 發布者預先建立並隨應用程式提供，使用者只在 Google 官方頁面登入並同意寄信權限。

流程如下：

1. 使用者按下「建立並寄送備份」。
2. 系統檢查 Windows Credential Manager 中是否存在有效的 Gmail refresh token。
3. 若為第一次使用或沒有可用 token，顯示授權說明，並以系統預設瀏覽器開啟 Google OAuth 2.0 登入與同意畫面；授權成功後安全保存 refresh token，並繼續本次寄送。
4. 若已有 refresh token，系統在需要時靜默換取新的 access token，不顯示登入畫面。
5. 系統建立並驗證新的 ZIP 備份。
6. 顯示備份內容摘要，並帶入設定中保存的預設收件人；使用者可確認或修改收件人與郵件內容。
7. 系統將 ZIP 附加到 Gmail。
8. 寄送成功後記錄結果，並保留這次產生的本機 ZIP。
9. 寄送失敗時保留本機 ZIP，並顯示錯誤訊息。

收件人可以是任意合法電子郵件地址。使用者可在設定頁預先保存預設收件人，後續寄送時自動帶入，不需要每次重新輸入。

郵件本文應列出寄送當天的今日任務與逾期任務，內容可以包含：

- 任務名稱。
- 任務說明。
- 分類與標籤。
- 複習日期。
- 完成狀態。
- 備份建立時間。
- 備份檔案名稱。

實際郵件樣式可以在後續討論後決定。即使郵件本文包含任務內容，完整資料仍以 ZIP 附件為準。每次手動寄送所產生的 ZIP 都保留在本機 `backups` 目錄，v9 不自動刪除，由使用者自行管理。

本機應保留寄送紀錄，包括：

- 寄送時間。
- 收件人。
- 備份檔名。
- 備份 checksum。
- 寄送成功或失敗。
- 錯誤訊息。
- Gmail message ID，如 API 可以取得。

Gmail 寄送使用 Gmail API OAuth 2.0。首次授權必須要求 offline access，以取得可跨程式重啟使用的 refresh token。OAuth token 與其他敏感認證資料不可直接寫入程式碼、備份 ZIP 或一般 SQLite 設定表，應由 Windows Credential Manager 或等效的安全儲存機制保存。

設定頁應顯示目前連結的 Gmail 帳號與連結狀態，並提供「連結 Gmail」、「重新授權」及「解除連結」。解除連結時應移除本機 token，並在可行時撤銷 Google 端授權。

若 refresh token 因使用者撤銷授權、長期未使用、密碼或帳號安全狀態變更、Google Workspace 管理政策或其他原因失效，系統應將帳號標記為需要重新授權；下次使用者主動寄送時才重新開啟 OAuth 流程，不得在背景自行要求授權。

OAuth 的 offline access 只用於跨程式重啟保存授權及更新 access token，不代表允許背景寄送。若程式完全關閉，v9 不會執行寄送。未來若要支援關閉後寄送，可以另行評估 Windows 工作排程器或雲端服務，但不列入目前版本。

## 4. 資料庫與 DBMS 設計

### 4.1 SQLite 選擇理由

目前建議繼續使用 SQLite，因為本專案是單機 Windows、單一使用者，不需要多人同時連線，也不需要雲端同步。

SQLite 的優點：

- 不需要安裝資料庫伺服器。
- 不需要網路即可使用。
- 資料可集中在單一資料庫檔案。
- 備份與搬移簡單。
- 適合 Windows exe 部署。
- 測試時容易建立暫存資料庫。

SQLite 的限制：

- 多人同時寫入能力不如伺服器型資料庫。
- 不適合直接作為多人雲端同步資料庫。
- 若未來支援多裝置同步，需要額外的同步服務。

PostgreSQL、MySQL、MariaDB 等伺服器型 DBMS 目前都會增加安裝、維護與部署成本，因此暫時不採用。如果未來增加帳號、雲端或多人協作，可以在資料存取層後方增加 PostgreSQL 服務，而不必大幅改寫 UI 與業務邏輯。

### 4.2 SQLite 實作要求

- 啟用 Foreign Key。
- 視需要使用 WAL mode。
- 使用 transaction 保護批次操作。
- 建立 schema version。
- 提供 migration 機制。
- 匯入、刪除與還原失敗時可 rollback。
- 提供 `PRAGMA integrity_check`。
- 使用 SQLite backup API 建立一致性的資料庫快照。
- 任務、複習紀錄、設定、素材與寄送紀錄使用清楚的資料表分離管理。

建議資料表：

- `tasks`：任務基本資料、目前狀態與暫停日期。
- `review_schedules`：預定複習時間與目前狀態。
- `review_records`：完成、略過、推延與合併等歷史紀錄。
- `categories`：分類資料。
- `tags`：標籤資料。
- `task_tags`：任務與標籤關聯。
- `settings`：個人化與應用程式設定。
- `assets`：背景與貼圖的相對路徑及狀態。
- `backup_logs`：備份與 Gmail 寄送紀錄。

### 7.4 手動功能驗收

#### 任務與排程

- 建立遺忘曲線任務後，複習日期數量與間隔正確。
- 手動日期不可重複，也不可早於開始時間。
- 編輯任務後，畫面與資料庫內容一致。
- 修改開始時間、複習次數或排程模式時，只重建尚未處理的排程並顯示差異預覽。
- 新複習次數低於已完成數與已略過數的總和時，系統拒絕修改。
- 刪除任務後，不留下孤立複習資料。
- 封存任務後，不出現在預設的進行中列表。
- 暫停期間不累積逾期，恢復後未處理排程依暫停天數順延。

#### 複習

- 完成一筆複習後，完成率正確更新。
- 所有複習完成後，任務狀態變成已完成。
- 略過不算完成、不可復原，並使完成率下降。
- 已無待處理項目但含有略過項目時，任務狀態變成未完全完成。
- 推到明天後，目前與後續未處理項目均增加一個日曆日並保留時分。
- 推延造成相同日期時間時會合併排程並留下歷史紀錄。
- 已完成與已略過項目不會被推延。
- 逾期項目可以被查詢與處理。
- 今天較早時間的項目仍屬今日，不會因時分而變成逾期。

#### 搜尋與月曆

- 可以依名稱、分類與標籤找到任務。
- 月曆日期數量與資料庫一致。
- 點擊日期後只顯示該日項目。
- 不同視窗大小下按鈕與文字仍可使用。

#### 備份與匯入

- ZIP 包含資料庫、背景、貼圖與 manifest。
- 匯入 ZIP 後任務、排程、設定、素材與歷史紀錄完全取代目前資料。
- 不同備份格式版本或 SQLite schema 版本的 ZIP 會被拒絕。
- Gmail 認證、既有本機備份 ZIP 與文字日誌不會被匯入內容取代。
- 匯入成功後會要求重新啟動，重啟後背景與貼圖可以正常顯示。
- 錯誤 ZIP 不會破壞目前資料。
- 未加密 ZIP 的內容可以被正常讀取，符合目前需求。

#### Gmail

- 使用者按鈕才能觸發寄送。
- 第一次使用 Gmail 帳號寄送時，會由系統預設瀏覽器完成 OAuth 授權。
- 第一次授權完成後，關閉再重新開啟程式並按下寄送，不會再次要求登入。
- access token 過期時會使用安全保存的 refresh token 靜默更新。
- refresh token 失效時會顯示重新授權流程，而不會遺失已建立的 ZIP。
- ZIP 會正確附加。
- 設定中的預設收件人會自動帶入，並可在寄送前修改。
- 郵件本文可以顯示當天的今日任務與逾期任務。
- 寄送成功會留下紀錄。
- 寄送成功或失敗都會保留本機備份。
- OAuth token 不會寫入程式碼、SQLite 一般設定或備份 ZIP。
- 解除連結會移除本機 token，之後寄送時重新進入首次授權流程。
- 程式關閉時不會偷偷執行寄送。

## 10. 技術需求

### 10.1 執行環境

- 主要作業系統：Windows 10 以上，優先支援 Windows 10 與 Windows 11。
- 開發語言：Python 3.10 以上。
- 使用者不應需要另外安裝 Python 才能執行正式 `.exe`。
- 正式版本應支援常見的 1280×720、1920×1080 與高 DPI 螢幕。
- 應用程式資料必須放在使用者有權限寫入的資料目錄，不應依賴目前工作目錄。
- 建議資料目錄使用 Windows 使用者的 Local AppData，例如：

```text
%LOCALAPPDATA%\RenewCurve\
├── renew_curve.db
├── assets\
├── backups\
└── logs\
```

OAuth token 由 Windows Credential Manager 或等效安全儲存機制管理，不存放在上述一般應用程式資料目錄中。

### 10.2 主要套件

正式依賴：

- `PySide6`：桌面 GUI。
- Python 內建 `sqlite3`：SQLite 資料庫存取。
- Python 內建 `zipfile`：ZIP 備份建立與讀取。
- Python 內建 `hashlib`：checksum 計算。
- Python 內建 `logging`：錯誤與操作紀錄。

開發依賴：

- `pytest`：自動化測試。
- `pytest-qt` 或等效 Qt 測試工具：GUI 測試。
- `PyInstaller`：Windows 執行檔打包。
- 程式格式化、lint 與型別檢查工具，可依實作團隊選擇。

Gmail 寄送應加入 Gmail API OAuth 2.0 所需套件。Gmail 認證套件不應被寫死在 UI 層，應由獨立的 Gmail service 負責。

### 10.3 應用程式啟動需求

啟動時應依序完成：

1. 確認應用程式資料目錄。
2. 建立必要的 `assets`、`backups` 與 `logs` 子目錄。
3. 建立或開啟 SQLite 資料庫。
4. 檢查資料庫 schema version。
5. 執行尚未完成的 migration。
6. 啟用 Foreign Key 與建議的 SQLite 設定。
7. 載入個人化設定。
8. 載入背景與貼圖清單。
9. 載入儀表板資料。

如果資料庫無法開啟，程式應顯示錯誤原因與可執行的處理方式，不應直接覆蓋原始資料。

### 10.4 SQLite 技術需求

- 使用 SQLite 作為主要 DBMS。
- 連線時執行 `PRAGMA foreign_keys = ON`。
- 可使用 WAL mode 改善讀寫並行能力。
- 所有跨多張資料表的操作必須使用 transaction。
- 任務建立、批次複習建立與 ZIP 匯入必須支援 rollback。
- 建立 `schema_version` 或等效 migration 表。
- 每次 schema 變更都要新增 migration，不可直接刪除或覆蓋舊欄位。
- 所有資料庫查詢使用參數化 SQL。
- 日期時間使用一致的 ISO 8601 本機時間格式儲存，不附加時區位移。
- 素材使用相對路徑，不儲存依賴特定電腦的絕對路徑。
- 匯入前後都應執行資料庫完整性檢查。

建議的主要資料表：

```text
tasks              任務基本資料
review_schedules   預定複習時間與目前狀態
review_records     完成、略過、推延等歷史紀錄
categories         任務分類
tags               任務標籤
task_tags          任務與標籤的關聯
settings           個人化與應用程式設定
assets             背景與貼圖檔案資訊
backup_logs        備份建立與 Gmail 寄送紀錄
schema_migrations  資料庫版本與 migration 紀錄
```

### 10.5 日期與時間需求

- 儲存格式應統一，例如 ISO 8601。
- 顯示格式使用中文或容易理解的本地格式。
- 建立排程時保留使用者指定的時分。
- 遺忘曲線第 N 天以開始時間增加 N 個 24 小時計算。
- 手動日期不得重複。
- 手動日期不得早於任務開始時間。
- 查詢今日任務時應以使用者本機日期為準。
- 預定日期早於本機今天才算逾期；同一天內不以時分判定逾期。
- 未來摘要固定為包含今天的 7 個本機日曆日。
- 推到明天使用本機日曆日加一天，保留原時分，並正確處理跨月與跨年。
- v9 不做時區換算。使用者改變 Windows 時區後，既有排程仍保持原本儲存的牆上日期與時間。

### 10.6 ZIP 備份技術需求

- ZIP 必須包含 `manifest.json` 與資料庫檔案。
- ZIP 可包含背景與貼圖等素材。
- 資料庫快照包含個人化設定、備份紀錄與 Gmail 寄送紀錄，但 ZIP 不包含 Gmail 認證、既有備份 ZIP 或文字日誌。
- ZIP 建立時應使用一致性的 SQLite backup snapshot。
- 每個檔案應可計算 SHA-256 checksum。
- 匯入前必須檢查 ZIP 檔案清單。
- 不允許 `..`、絕對路徑或其他離開暫存資料夾的路徑。
- 不直接將未驗證內容解壓縮到正式資料目錄。
- 匯入應先解壓縮至暫存目錄。
- 匯入只接受與目前程式完全相同的備份格式版本及 SQLite schema 版本。
- 確認所有檔案正確後，才替換目前資料。
- 替換失敗時必須能恢復匯入前資料。
- 替換成功後必須關閉舊資料庫連線並要求重新啟動程式。
- 目前不要求加密，但應在介面提醒 ZIP 內容未加密。
- 備份副檔名固定使用 `.zip`。

### 10.7 Gmail 寄送技術需求

- Gmail 寄送只能由使用者按鈕觸發。
- Gmail 寄送使用 Gmail API OAuth 2.0。
- OAuth 用戶端設定由 Renew Curve 發布者提供；一般使用者介面不得要求輸入 Gmail 密碼、API key、client secret 或手動建立認證文件。
- 程式關閉時不執行背景寄送。
- 首次授權使用系統預設瀏覽器與 Desktop app loopback redirect，不使用內嵌瀏覽器或手動複製授權碼。
- OAuth 請求必須使用 offline access 取得 refresh token，並使用 `state` 與 PKCE 等機制保護授權流程。
- 應用程式重新啟動後，寄送時使用已保存的 refresh token 靜默更新 access token，不再次要求使用者登入。
- refresh token 無效或被撤銷時，只有在使用者主動使用 Gmail 功能時才要求重新授權。
- 寄送前先產生並驗證 ZIP。
- 設定頁可保存任意合法的預設收件人，寄送前自動帶入並允許修改。
- 寄送服務必須與 UI 分離。
- 網路錯誤、認證失敗、附件過大與 Gmail API 錯誤都要被捕捉。
- 寄送成功或失敗時，ZIP 都必須保留在本機，v9 不自動清除。
- 寄送成功或失敗都要寫入 `backup_logs`。
- Gmail OAuth token 不可寫入程式碼、ZIP 或一般設定資料，應存入 Windows Credential Manager 或等效安全儲存機制。
- 設定頁應顯示連結狀態及 Gmail 帳號，並提供連結、重新授權與解除連結操作。
- 正式散布版本不得長期維持在 Google OAuth 外部 Testing 狀態；使用 `gmail.send` 權限時應完成正式發布所需的 OAuth 設定與驗證，避免測試用 refresh token 到期後頻繁要求登入。
- Gmail 寄送操作不應阻塞主畫面，必要時使用背景 worker。
- 寄送過程應提供處理中、成功與失敗狀態。

郵件本文列出當天的今日任務與逾期任務，可包含任務名稱、筆記、分類、複習日期與完成狀態；完整資料仍以 ZIP 附件為主要還原來源。

### 10.8 GUI 技術需求

- UI 層不可直接撰寫 SQL。
- UI 層不可直接處理 ZIP 內部格式。
- UI 層不可直接管理 Gmail 認證細節。
- 長時間操作不可阻塞 Qt event loop。
- 大量資料列表應使用適當的模型或分頁方式。
- 所有對話框必須支援取消與錯誤返回。
- 不使用硬編碼固定視窗尺寸作為唯一版面策略。
- 介面元件應可在不同 DPI 與視窗尺寸下重新排列。
- 顏色與文字應維持足夠對比度。
- 重要操作需要成功、失敗或確認提示。

### 10.9 日誌與錯誤處理

應記錄但不可洩漏敏感資料的事件包括：

- 應用程式啟動與關閉。
- 資料庫初始化與 migration。
- 任務建立、修改、刪除與封存。
- 備份建立與匯入結果。
- Gmail 寄送結果。
- 未預期的例外。

日誌不得記錄：

- Gmail 密碼。
- OAuth token。
- 完整的敏感認證內容。

錯誤訊息應提供一般使用者看得懂的內容，詳細 traceback 則寫入 log 供開發者分析。

## 11. 系統架構

### 11.1 分層架構

v9 建議採用分層架構，讓 UI、業務規則、資料庫與外部服務互相解耦。

```text
┌──────────────────────────────┐
│ Presentation Layer            │
│ PySide6 Windows UI           │
│ Pages / Dialogs / ViewModels │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ Application / Service Layer  │
│ TaskService                  │
│ ReviewService                │
│ BackupService                │
│ GmailService                 │
│ SettingsService              │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ Domain Layer                 │
│ Task / Review models         │
│ Forgetting curve rules       │
│ Validation / progress rules  │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ Infrastructure Layer         │
│ SQLite repositories          │
│ Migration                    │
│ ZIP file storage             │
│ File system / logging        │
│ Gmail adapter                │
└──────────────────────────────┘
```

### 11.2 Presentation Layer

Presentation Layer 負責：

- 顯示頁面與元件。
- 接收使用者操作。
- 顯示資料與錯誤訊息。
- 呼叫 Application Service。
- 根據 Service 回傳結果刷新畫面。

Presentation Layer 不負責：

- 直接查詢 SQLite。
- 直接建立 ZIP。
- 直接寄送 Gmail。
- 實作遺忘曲線演算法。

建議畫面元件：

```text
ui/
├── app_shell.py
├── navigation.py
├── dashboard_page.py
├── tasks_page.py
├── review_page.py
├── calendar_page.py
├── backup_page.py
├── settings_page.py
├── task_dialog.py
└── common_widgets.py
```

導覽列不固定在左側，由 `app_shell` 與 `navigation` 負責根據版面需求配置。

### 11.3 Application / Service Layer

Service Layer 負責協調畫面操作與底層資料操作。

建議服務：

#### `TaskService`

- 建立任務。
- 編輯任務。
- 刪除任務。
- 暫停與恢復任務，並順延未處理排程。
- 封存與還原任務。
- 複製任務。
- 搜尋與篩選任務。
- 重新計算並保存任務狀態。

#### `ReviewService`

- 產生固定遺忘曲線。
- 驗證手動複習日期。
- 查詢今日、逾期與未來複習。
- 完成複習。
- 略過複習。
- 將目前與後續未處理複習整批推到明天，並處理重複排程合併。
- 更新任務進度。

#### `BackupService`

- 建立 SQLite snapshot。
- 收集背景與貼圖素材。
- 產生 manifest。
- 建立 ZIP。
- 驗證 ZIP。
- 完整取代式匯入。
- 建立匯入前還原點。

#### `GmailService`

- 管理 Gmail API OAuth 2.0 認證介面。
- 管理首次授權、refresh token 安全保存與 access token 靜默更新。
- 管理重新授權、解除連結及 token 失效處理。
- 建立郵件本文。
- 附加 ZIP。
- 寄送郵件。
- 回傳寄送結果。
- 不將認證細節暴露給 UI。

#### `SettingsService`

- 讀取設定。
- 儲存設定。
- 驗證設定值。
- 管理背景與貼圖選擇。
- 管理 Gmail 預設收件人。
- 管理資料目錄。

### 11.4 Domain Layer

Domain Layer 放置不依賴 PySide6、SQLite 或 Gmail 的核心規則。

建議放置：

```text
domain/
├── models.py
├── enums.py
├── scheduler.py
├── validators.py
├── progress.py
└── errors.py
```

Domain Layer 應可在沒有 GUI 的情況下單獨測試。

主要規則包括：

- 遺忘曲線日期計算。
- 複習日期排序與重複檢查。
- 日期與時間驗證。
- 任務狀態轉換。
- 完成率計算。
- 推延範圍判定。
- 暫停期間與恢復後的日期順延。
- 略過與未完全完成規則。
- 匯入資料格式驗證。

### 11.5 Infrastructure Layer

Infrastructure Layer 負責實際與作業系統、資料庫、檔案和外部服務溝通。

建議結構：

```text
infrastructure/
├── database/
│   ├── connection.py
│   ├── migrations.py
│   ├── repositories.py
│   └── schema.sql
├── backup/
│   ├── archive.py
│   ├── manifest.py
│   └── validator.py
├── gmail/
│   ├── client.py
│   ├── auth.py
│   └── mail_builder.py
├── files/
│   └── asset_store.py
└── logging_config.py
```

Infrastructure Layer 應提供清楚的介面，讓測試時可以使用 fake repository、fake Gmail client 或暫存資料夾。

### 11.7 依賴方向

模組依賴方向應維持：

```text
UI → Application Services → Domain
                         ↓
                  Infrastructure
```

限制如下：

- Domain 不可依賴 PySide6。
- Domain 不可依賴 Gmail SDK。
- UI 不可直接依賴 SQLite connection。
- UI 不可自行處理 ZIP 路徑安全。
- Gmail Service 不可修改 UI 元件。
- Repository 不可包含畫面邏輯。

### 11.8 外部服務失效時的行為

Gmail 無法使用時：

- 本機任務與複習功能仍可正常使用。
- 本機 ZIP 備份仍可建立。
- 只有 Gmail 寄送功能顯示錯誤。
- ZIP 不可因寄送失敗而被刪除。

這能確保 Gmail 只是備份傳送管道，不會成為整個應用程式的必要依賴。
